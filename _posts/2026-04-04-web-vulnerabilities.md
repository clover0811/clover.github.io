웹 애플리케이션은 사용자의 입력을 받고, 서버에서 요청을 처리한 뒤, 데이터베이스와 통신하며 결과를 다시 사용자에게 보여준다. 이 과정에서 입력값 처리, 인증, 권한 확인, 세션 관리, 파일 처리, 데이터 출력 방식 중 하나라도 안전하게 설계되지 않으면 취약점이 발생할 수 있다.

웹 취약점은 각각 이름과 공격 방식은 다르지만, 공통적으로 다음과 같은 상황에서 자주 발생한다.

- 사용자 입력값을 신뢰하는 경우
- 서버 측 검증이 부족한 경우
- 인증과 인가를 구분하지 못한 경우
- 민감한 기능에 대한 권한 확인이 부족한 경우
- 데이터 출력 과정에서 안전한 처리가 이루어지지 않은 경우
- 파일 업로드나 다운로드 과정에서 검증이 부족한 경우

# 웹 취약점을 이해할 때 중요한 관점

웹 취약점을 공부할 때는 단순히 공격 구문이나 예시만 외우는 것보다, 취약점이 발생하는 구조를 이해하는 것이 중요하다.

대부분의 웹 취약점은 다음 질문과 연결된다.

> 사용자의 입력값을 서버가 어떻게 처리하는가?  
> 사용자가 해당 기능이나 데이터에 접근할 권한이 있는가?  
> 서버가 클라이언트에서 전달된 값을 그대로 신뢰하고 있지는 않은가?  
> 출력되는 데이터가 브라우저에서 코드처럼 해석될 가능성은 없는가?

웹 서비스는 사용자의 요청을 기반으로 동작한다. 하지만 사용자의 요청은 언제든지 조작될 수 있다. 따라서 서버는 클라이언트에서 전달된 값을 그대로 신뢰해서는 안 되며, 중요한 검증은 반드시 서버 측에서 수행해야 한다.

## 웹 보안에서 자주 등장하는 취약점

- SQL Injection
- XSS
- CSRF
- Authentication / Session
- Broken Access Control / IDOR
- File Upload


## 1. SQL Injection

### SQL Injection이란?

SQL Injection은 사용자 입력값이 SQL 쿼리의 일부로 잘못 해석되어 실행되는 취약점이다.

웹 서비스는 로그인, 검색, 게시글 조회, 상품 조회 등의 기능에서 데이터베이스에 SQL 쿼리를 보낸다. 이때 사용자 입력값을 안전하게 처리하지 않고 SQL 문자열에 직접 이어 붙이면, 공격자가 SQL 문법을 삽입해 쿼리 구조를 조작할 수 있다.

핵심은 다음과 같다.

> 원래는 데이터로 처리되어야 할 사용자 입력값이 SQL 명령어처럼 해석될 때 SQL Injection이 발생한다.

### 발생 원인

SQL Injection은 주로 다음과 같은 상황에서 발생한다.

- 사용자 입력값을 SQL 문자열에 직접 연결하는 경우
- Prepared Statement를 사용하지 않는 경우
- 입력값 검증이 부족한 경우
- 데이터베이스 에러 메시지가 그대로 노출되는 경우
- DB 계정에 과도한 권한이 부여된 경우

예를 들어 로그인 기능에서 사용자가 입력한 아이디와 비밀번호가 SQL 쿼리에 직접 삽입된다면, 공격자는 입력값을 조작해 인증 조건을 우회하려고 시도할 수 있다.

### 공격으로 이어지는 흐름

SQL Injection은 단순히 로그인 우회에만 사용되는 취약점이 아니다. 데이터베이스에 접근할 수 있다는 것은 서비스 내부의 중요한 데이터에 영향을 줄 수 있다는 뜻이다.

SQL Injection이 발생하면 다음과 같은 공격으로 이어질 수 있다.

- 인증 우회
- 사용자 정보 조회
- 게시글, 주문 내역 등 데이터 조회
- 데이터 변조 또는 삭제
- 관리자 계정 정보 탈취
- 다른 취약점과 결합한 추가 공격

특히 사용자 정보나 비밀번호 해시가 노출되면 계정 탈취나 추가적인 인증 공격으로 이어질 수 있다.

### 다른 취약점과의 연결

SQL Injection은 다른 취약점과 연결될 수 있다.

예를 들어 SQL Injection으로 데이터베이스에 악성 스크립트를 저장할 수 있고, 그 데이터가 웹페이지에 그대로 출력된다면 Stored XSS로 이어질 수 있다.

또한 관리자 계정 정보가 유출되면 관리자 페이지 접근, 권한 오남용, 내부 기능 악용으로 이어질 수 있다.

즉, SQL Injection은 데이터베이스에만 영향을 주는 것이 아니라 서비스 전체의 보안에 영향을 줄 수 있다.

### 방어 방법

SQL Injection을 방어하기 위해서는 다음과 같은 방법이 필요하다.

- Prepared Statement 사용
- Parameterized Query 사용
- ORM 사용 시 안전한 쿼리 작성 방식 유지
- 사용자 입력값 검증
- DB 계정 최소 권한 적용
- 불필요한 에러 메시지 노출 방지
- 민감한 데이터 암호화
- 비밀번호는 안전한 해시 알고리즘으로 저장

가장 중요한 방어 방법은 Prepared Statement 또는 Parameterized Query를 사용하는 것이다. 이 방식은 SQL 쿼리 구조와 사용자 입력값을 분리해서 처리하므로, 입력값이 SQL 문법으로 해석되는 것을 막을 수 있다.

## 2. XSS

### XSS란?

XSS는 Cross-Site Scripting의 약자이다. 사용자 입력값이 웹페이지에 안전하게 출력되지 않아, 다른 사용자의 브라우저에서 스크립트가 실행되는 취약점이다.

SQL Injection이 데이터베이스 쿼리 처리 과정에서 발생하는 문제라면, XSS는 브라우저에서 입력값이 HTML 또는 JavaScript로 해석될 때 발생하는 문제라고 볼 수 있다.

핵심은 다음과 같다.

> 사용자 입력값이 데이터가 아니라 브라우저에서 실행 가능한 코드로 해석될 때 XSS가 발생한다.

### XSS의 주요 종류

XSS는 대표적으로 다음 세 가지로 나눌 수 있다.

- Stored XSS
- Reflected XSS
- DOM-based XSS

### Stored XSS

Stored XSS는 악성 스크립트가 서버에 저장된 뒤, 다른 사용자가 해당 페이지를 볼 때 실행되는 방식이다.

예를 들어 게시글, 댓글, 닉네임, 프로필 소개, 리뷰 기능에서 사용자가 입력한 값이 제대로 처리되지 않고 저장된다면 Stored XSS가 발생할 수 있다.

Stored XSS는 한 번 저장되면 여러 사용자에게 반복적으로 영향을 줄 수 있기 때문에 위험도가 높은 편이다.

### Reflected XSS

Reflected XSS는 입력값이 서버에 저장되지는 않고, 요청에 포함된 값이 응답 페이지에 그대로 반사되면서 실행되는 방식이다.

예를 들어 검색어, 오류 메시지, URL 파라미터 등이 페이지에 그대로 출력될 때 발생할 수 있다. 공격자는 악성 스크립트가 포함된 링크를 피해자에게 전달하고, 피해자가 해당 링크를 클릭하면 스크립트가 실행될 수 있다.

### DOM-based XSS

DOM-based XSS는 서버 응답보다는 브라우저에서 실행되는 JavaScript 코드의 처리 과정에서 발생하는 XSS이다.

예를 들어 프론트엔드 코드가 URL 파라미터 값을 읽어와 innerHTML에 직접 삽입하는 경우, 입력값이 브라우저에서 코드로 해석될 수 있다.

즉, DOM-based XSS는 클라이언트 측 JavaScript가 DOM을 안전하지 않게 조작할 때 발생한다.

### 공격으로 이어지는 흐름

XSS가 발생하면 공격자는 피해자의 브라우저에서 스크립트를 실행할 수 있다. 이로 인해 다음과 같은 문제가 발생할 수 있다.

- 페이지 변조
- 피싱 화면 삽입
- 사용자 입력값 탈취
- 사용자의 권한으로 요청 전송
- 세션 탈취 시도
- 관리자 페이지에서 발생할 경우 관리자 기능 악용

XSS는 단순히 알림창을 띄우는 문제가 아니다. 피해자가 로그인한 상태라면, 공격 스크립트가 피해자의 권한으로 특정 요청을 보낼 수 있기 때문에 위험하다.

### 다른 취약점과의 연결

XSS는 여러 취약점과 연결될 수 있다.

쿠키에 HttpOnly 설정이 없다면 JavaScript를 통해 세션 쿠키 탈취가 가능할 수 있다. 또한 피해자 브라우저에서 요청을 보낼 수 있으므로 CSRF와 비슷한 효과를 낼 수도 있다.

파일 업로드 기능에서 SVG나 HTML 파일을 안전하게 처리하지 않으면 File Upload 취약점이 XSS로 이어질 수도 있다.

### 방어 방법

XSS를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 출력 위치에 맞는 인코딩 적용
- 사용자 입력값 검증
- HTML Sanitization 적용
- Content Security Policy, CSP 설정
- 쿠키에 HttpOnly, Secure, SameSite 속성 적용
- 사용자 입력값을 innerHTML 등에 직접 삽입하지 않기
- 안전하지 않은 DOM API 사용 주의

XSS 방어에서 중요한 것은 입력값 검증만으로는 부족하다는 점이다. 입력값이 어디에 출력되는지에 따라 필요한 처리가 달라진다.

예를 들어 HTML 본문에 출력되는 값, HTML 속성에 들어가는 값, JavaScript 코드 내부에 들어가는 값은 각각 다른 방식으로 처리해야 한다.

## 3. CSRF

### CSRF란?

CSRF는 Cross-Site Request Forgery의 약자이다. 사용자가 로그인된 상태를 악용해, 사용자의 의도와 다르게 요청을 보내게 만드는 공격이다.

웹 브라우저는 특정 사이트에 로그인된 상태라면, 해당 사이트로 요청을 보낼 때 쿠키를 자동으로 포함한다. 공격자는 이 특성을 이용해 사용자가 원하지 않는 요청을 보내도록 유도할 수 있다.

핵심은 다음과 같다.

> 사용자가 로그인된 상태에서 브라우저가 자동으로 인증 정보를 포함해 요청을 보내는 특성을 악용하는 공격이다.

### 발생 가능한 기능

CSRF는 주로 서버의 상태를 변경하는 기능에서 문제가 된다.

예를 들면 다음과 같은 기능이 있다.

- 비밀번호 변경
- 이메일 변경
- 게시글 작성
- 댓글 작성
- 회원 탈퇴
- 배송지 변경
- 결제 요청
- 관리자 설정 변경

단순 조회 기능보다는 서버의 데이터나 사용자의 계정 상태를 변경하는 기능에서 더 위험하다.

### 공격으로 이어지는 흐름

CSRF의 일반적인 흐름은 다음과 같다.

1. 사용자가 특정 웹사이트에 로그인한 상태를 유지하고 있다.
2. 공격자가 사용자를 악성 페이지나 링크로 유도한다.
3. 사용자의 브라우저가 공격자가 의도한 요청을 대상 사이트로 보낸다.
4. 브라우저는 로그인 쿠키를 자동으로 포함한다.
5. 서버가 추가 검증 없이 요청을 처리하면 사용자의 의도와 다른 행동이 수행된다.

### XSS와의 차이

XSS와 CSRF는 모두 사용자의 브라우저와 관련이 있지만 핵심이 다르다.

- XSS는 공격자의 스크립트가 피해자 브라우저에서 실행되는 문제이다.
- CSRF는 피해자 브라우저가 로그인된 상태로 위조된 요청을 보내는 문제이다.

즉, XSS는 코드 실행 문제이고, CSRF는 요청 위조 문제라고 볼 수 있다.

### 다른 취약점과의 연결

CSRF는 세션 관리와 밀접하게 연결된다. 세션 만료 시간이 너무 길거나 SameSite 쿠키 설정이 없다면 CSRF 위험이 커질 수 있다.

또한 XSS가 존재하면 CSRF 토큰을 탈취하거나 정상 요청처럼 위조할 수 있으므로, CSRF 방어가 무력화될 수 있다.

관리자 기능에 CSRF가 존재한다면 관리자 권한으로 설정 변경이나 계정 조작이 발생할 수 있다.

### 방어 방법

CSRF를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- CSRF Token 사용
- SameSite 쿠키 설정
- 중요한 기능에서 재인증 요구
- GET 요청으로 상태 변경 금지
- Origin 또는 Referer 헤더 검증
- CORS 설정 주의

CSRF Token은 서버가 예측하기 어려운 토큰을 발급하고, 상태 변경 요청마다 해당 토큰이 함께 전달되는지 확인하는 방식이다.

공격자는 피해자의 브라우저가 쿠키를 자동으로 보내도록 만들 수는 있지만, 정상 페이지에 포함된 CSRF Token까지 알기는 어렵다.

## 4. Authentication / Session

### Authentication과 Session이란?

Authentication은 사용자가 누구인지 확인하는 과정이다. Session은 인증된 사용자의 로그인 상태를 유지하는 방식이다.

간단히 정리하면 다음과 같다.

- Authentication: 사용자가 누구인지 확인
- Session: 로그인 상태 유지
- Authorization: 특정 기능이나 데이터에 접근할 권한이 있는지 확인

인증과 세션 관리가 부실하면 계정 탈취, 인증 우회, 세션 탈취, 무차별 대입 공격 등으로 이어질 수 있다.

### 대표적인 취약점

Authentication / Session과 관련된 대표적인 취약점은 다음과 같다.

- 약한 비밀번호 정책
- 로그인 실패 제한 없음
- 무차별 대입 공격 방어 부족
- 세션 만료 시간 없음
- 로그아웃 후 세션 무효화 미흡
- 세션 ID 예측 가능
- 로그인 후 세션 ID 재발급 없음
- 비밀번호 재설정 토큰이 예측 가능하거나 만료되지 않음
- 쿠키 보안 속성 부족
- MFA 미적용

### 주요 공격 방식

#### Brute Force

Brute Force는 가능한 비밀번호를 계속 대입해 로그인에 성공하려는 공격이다. 로그인 실패 제한이나 Rate Limiting이 없다면 자동화된 방식으로 많은 로그인을 시도할 수 있다.

#### Credential Stuffing

Credential Stuffing은 다른 서비스에서 유출된 아이디와 비밀번호 조합을 이용해 로그인을 시도하는 공격이다.

사용자가 여러 서비스에서 같은 비밀번호를 사용한다면, 한 곳에서 유출된 계정 정보가 다른 서비스에서도 악용될 수 있다.

#### Session Hijacking

Session Hijacking은 세션 ID나 인증 토큰이 탈취되어 공격자가 로그인한 사용자처럼 행동하는 공격이다.

XSS, 네트워크 도청, 안전하지 않은 쿠키 설정 등이 세션 탈취로 이어질 수 있다.

#### Session Fixation

Session Fixation은 공격자가 미리 정한 세션 ID를 피해자에게 사용하게 만들고, 피해자가 로그인한 뒤 해당 세션을 공격자가 사용하는 방식이다.

로그인 이후 세션 ID를 새로 발급하지 않으면 이런 문제가 발생할 수 있다.

### 다른 취약점과의 연결

Authentication / Session 취약점은 다른 취약점과 연결되기 쉽다.

XSS가 발생하고 쿠키 설정이 안전하지 않다면 세션 탈취로 이어질 수 있다. SQL Injection으로 사용자 계정 정보가 노출되면 인증 공격으로 이어질 수 있다. CSRF는 사용자가 로그인된 세션을 유지하고 있다는 점을 악용한다.

또한 인증에 성공했다고 해서 인가가 자동으로 해결되는 것은 아니다. 로그인한 사용자라도 접근 권한이 없는 데이터에 접근할 수 있다면 Broken Access Control 문제가 된다.

### 방어 방법

Authentication / Session 관련 취약점을 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 강한 비밀번호 정책 적용
- 로그인 실패 제한
- Rate Limiting 적용
- MFA 적용
- 세션 만료 시간 설정
- 로그인 후 세션 ID 재발급
- 로그아웃 시 서버 측 세션 무효화
- 쿠키에 HttpOnly, Secure, SameSite 속성 적용
- 비밀번호는 안전한 해시 알고리즘으로 저장
- 비밀번호 재설정 토큰은 예측 불가능하고 짧은 만료 시간을 가지도록 설정

인증과 세션은 웹 서비스의 기본 기능이지만, 보안적으로는 매우 중요한 영역이다. 로그인 기능은 단순히 아이디와 비밀번호를 확인하는 것에서 끝나는 것이 아니라, 세션 발급, 유지, 만료, 폐기까지 함께 고려해야 한다.

## 5. Broken Access Control / IDOR

### Broken Access Control이란?

Broken Access Control은 접근 통제가 제대로 이루어지지 않아, 사용자가 접근하면 안 되는 데이터나 기능에 접근할 수 있는 취약점이다.

웹 서비스에서는 사용자가 로그인했는지 확인하는 것뿐 아니라, 해당 사용자가 요청한 데이터나 기능에 접근할 권한이 있는지도 확인해야 한다.

예를 들어 일반 사용자가 관리자 페이지에 접근하거나, 다른 사용자의 개인정보를 조회할 수 있다면 접근 통제에 문제가 있는 것이다.

### IDOR이란?

IDOR은 Insecure Direct Object Reference의 약자이다. 객체를 직접 참조하는 값이 안전하게 보호되지 않아, 사용자가 파라미터를 조작해 다른 객체에 접근할 수 있는 취약점이다.

예를 들어 `/users/1001`이라는 URL이 있다고 가정한다.

현재 로그인한 사용자의 ID가 `1001`인데, URL을 `/users/1002`로 변경했을 때 다른 사용자의 정보가 보인다면 IDOR 취약점이 존재하는 것이다.

IDOR는 게시글, 주문 내역, 파일 다운로드, 프로필 조회, 결제 내역 등 다양한 기능에서 발생할 수 있다.

### 발생 원인

Broken Access Control과 IDOR는 주로 다음과 같은 이유로 발생한다.

- 로그인 여부만 확인하고 리소스 소유자 확인을 하지 않는 경우
- 서버 측 권한 검증이 부족한 경우
- 클라이언트에서 전달한 user_id, role 값을 그대로 신뢰하는 경우
- 관리자 기능에 대한 접근 제어가 부족한 경우
- 파일 다운로드 시 소유자 검증이 없는 경우
- 예측 가능한 ID만으로 리소스에 접근할 수 있는 경우

가장 중요한 점은 권한 검사는 반드시 서버에서 해야 한다는 것이다.

프론트엔드에서 버튼을 숨기거나 메뉴를 보이지 않게 하는 것은 보안 대책이 아니다. 공격자는 직접 API 요청을 보내거나 URL을 조작할 수 있기 때문에, 서버가 최종적으로 권한을 검증해야 한다.

### 공격으로 이어지는 흐름

Broken Access Control이나 IDOR가 발생하면 다음과 같은 문제가 생길 수 있다.

- 다른 사용자 개인정보 조회
- 다른 사용자 게시글 수정 또는 삭제
- 다른 사용자 주문 내역 조회
- 유료 기능 우회
- 관리자 기능 접근
- 파일 다운로드 권한 우회
- 내부 데이터 노출

특히 IDOR는 복잡한 공격 구문 없이도 파라미터 변경만으로 발견될 수 있기 때문에 실제 웹 서비스에서 중요한 취약점으로 다뤄진다.

### Authentication과 Authorization의 차이

Broken Access Control을 이해하려면 인증과 인가의 차이를 알아야 한다.

- Authentication: 사용자가 누구인지 확인하는 것
- Authorization: 해당 사용자가 특정 리소스에 접근할 권한이 있는지 확인하는 것

IDOR는 보통 인증이 된 상태에서 발생한다. 즉, 사용자는 로그인되어 있지만 자신이 접근하면 안 되는 데이터에 접근할 수 있는 상태가 문제다.

### 다른 취약점과의 연결

Broken Access Control은 여러 기능과 연결된다.

파일 다운로드 기능에서 `file_id`를 바꿨을 때 다른 사람의 파일을 받을 수 있다면 File Upload/Download 기능에서 IDOR가 발생한 것이다.

관리자 계정을 탈취한 상태에서 접근 통제까지 부실하다면 피해 범위가 더욱 커질 수 있다.

CSRF와 결합될 경우, 권한이 있는 사용자의 브라우저를 이용해 의도하지 않은 관리자 기능 실행이 발생할 수도 있다.

### 방어 방법

Broken Access Control과 IDOR를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 서버 측 권한 검증
- 객체 소유자 확인
- 역할 기반 접근 제어, RBAC 적용
- 기본 거부 정책 적용
- 클라이언트에서 전달된 권한 값 신뢰 금지
- 예측 가능한 ID만으로 접근 허용하지 않기
- 접근 실패 로그 기록
- 관리자 기능에 대한 별도 권한 검증
- 파일 다운로드 시 소유자 검증

접근 통제에서 중요한 원칙은 다음과 같다.

> 로그인 여부만 확인하는 것이 아니라, 사용자가 해당 리소스에 접근할 권한이 있는지 확인해야 한다.

## 6. File Upload

### File Upload 취약점이란?

File Upload 취약점은 파일 업로드 기능에서 허용되지 않은 파일이나 악성 파일이 업로드될 수 있을 때 발생하는 취약점이다.

파일 업로드 기능은 프로필 이미지, 게시판 첨부파일, 문서 업로드, 문의 파일 첨부 등 다양한 웹 서비스에서 사용된다. 하지만 업로드된 파일을 제대로 검증하지 않으면 서버 침해, XSS, 악성 파일 배포 등으로 이어질 수 있다.

### 발생 원인

File Upload 취약점은 주로 다음과 같은 상황에서 발생한다.

- 확장자 검증이 부족한 경우
- MIME 타입만 신뢰하는 경우
- 파일 내용 검증이 없는 경우
- 업로드 파일이 웹 루트 경로에 저장되는 경우
- 업로드된 파일에 실행 권한이 있는 경우
- 파일명 검증이 부족한 경우
- 파일 크기 제한이 없는 경우
- 다운로드 시 권한 검증이 없는 경우

단순히 확장자만 검사하는 것은 충분하지 않다. 파일명과 MIME 타입은 조작될 수 있기 때문에, 파일의 실제 내용과 저장 방식까지 고려해야 한다.

### 공격으로 이어지는 흐름

File Upload 취약점은 다음과 같은 공격으로 이어질 수 있다.

- 웹쉘 업로드
- 서버에서 악성 파일 실행
- HTML 또는 SVG 파일을 이용한 XSS
- 악성 파일 배포
- 서버 저장 공간 고갈
- 기존 파일 덮어쓰기
- 다른 사용자의 파일 다운로드

가장 위험한 경우는 서버에서 실행 가능한 파일이 업로드되고, 해당 파일에 웹으로 접근해 실행할 수 있는 상황이다. 이 경우 단순 파일 업로드 문제가 아니라 서버 침해로 이어질 수 있다.

### XSS와의 연결

파일 업로드 기능은 XSS와 연결될 수 있다.

예를 들어 SVG나 HTML 파일 업로드를 허용하고, 업로드된 파일이 브라우저에서 실행 가능한 형태로 제공된다면 스크립트가 실행될 수 있다.

따라서 이미지 업로드 기능이라고 하더라도 파일 확장자, MIME 타입, 파일 내용, 응답 헤더 등을 함께 고려해야 한다.

### IDOR와의 연결

파일 업로드 기능은 다운로드 기능과 함께 봐야 한다.

예를 들어 다운로드 URL이 `/download?file_id=10`이라고 가정한다.

현재 사용자의 파일이 `10`인데, `file_id`를 `11`로 변경했을 때 다른 사용자의 파일이 다운로드된다면 IDOR 취약점이 존재하는 것이다.

즉, 파일 업로드 기능에서는 업로드 검증뿐 아니라 다운로드 권한 검증도 중요하다.

### 방어 방법

File Upload 취약점을 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 허용 확장자 기반 검증
- 파일 시그니처 검증
- MIME 타입만 신뢰하지 않기
- 파일명 랜덤화
- 업로드 파일을 웹 루트 밖에 저장
- 업로드 경로에서 실행 권한 제거
- 파일 크기 제한
- 악성 파일 검사
- 다운로드 시 권한 검증
- 적절한 Content-Type과 Content-Disposition 헤더 설정

가장 중요한 것은 업로드된 파일이 서버에서 실행되지 않도록 하는 것이다. 또한 파일을 다운로드할 때는 요청한 사용자가 해당 파일에 접근할 권한이 있는지 반드시 확인해야 한다.

## 취약점 간 연결 흐름

웹 취약점은 하나만 단독으로 발생하기도 하지만, 여러 취약점이 연결되면서 더 큰 피해로 이어질 수 있다.

### SQL Injection → 계정 정보 유출 → 인증 공격

SQL Injection이 발생하면 데이터베이스의 사용자 정보가 노출될 수 있다. 만약 비밀번호 해시가 약하게 저장되어 있거나, 사용자가 다른 서비스와 같은 비밀번호를 사용한다면 계정 탈취로 이어질 수 있다.

### XSS → 세션 악용 → 사용자 권한으로 요청 수행

XSS가 발생하면 피해자 브라우저에서 공격자의 스크립트가 실행될 수 있다. 피해자가 로그인된 상태라면, 해당 권한으로 요청을 보내거나 페이지를 변조하는 공격이 가능해질 수 있다.

### CSRF → 로그인된 사용자 권한 악용

CSRF는 사용자가 로그인된 상태를 악용한다. 서버가 CSRF Token이나 SameSite 쿠키 같은 방어를 적용하지 않았다면, 사용자의 의도와 다른 상태 변경 요청이 처리될 수 있다.

### IDOR → 다른 사용자 데이터 노출

IDOR는 요청 파라미터를 조작해 다른 사용자의 데이터나 파일에 접근하는 문제다. 게시글, 주문 내역, 파일 다운로드, 프로필 조회 같은 기능에서 자주 생각해볼 수 있다.

### File Upload → XSS 또는 서버 침해

파일 업로드 검증이 부족하면 SVG, HTML 파일을 통한 XSS가 발생할 수 있고, 서버에서 실행 가능한 파일이 업로드되면 서버 침해로 이어질 수 있다.

## 정리

웹 취약점은 단순히 특정 공격 구문을 외우는 것보다, 서비스가 요청을 처리하는 구조를 이해하는 것이 중요하다.

이번 글에서 정리한 취약점들은 모두 웹 서비스의 기본 동작과 연결되어 있다.

- SQL Injection은 입력값이 SQL 쿼리로 해석될 때 발생한다.
- XSS는 입력값이 브라우저에서 스크립트로 해석될 때 발생한다.
- CSRF는 로그인된 사용자의 브라우저가 자동으로 인증 정보를 포함해 요청을 보내는 특성을 악용한다.
- Authentication / Session 취약점은 로그인과 세션 관리가 부실할 때 발생한다.
- Broken Access Control / IDOR는 권한 확인이 부족할 때 발생한다.
- File Upload 취약점은 업로드 파일에 대한 검증과 저장 방식이 부실할 때 발생한다.

각 취약점의 이름은 다르지만, 결국 중요한 원칙은 비슷하다.

> 사용자 입력값을 신뢰하지 말 것  
> 중요한 검증은 서버에서 수행할 것  
> 인증과 인가를 구분할 것  
> 데이터는 출력 위치에 맞게 안전하게 처리할 것  
> 업로드된 파일이 실행되지 않도록 할 것  
> 권한이 필요한 기능은 매 요청마다 검증할 것

웹 취약점을 공부할 때는 공격 예시만 보는 것이 아니라, 왜 발생했는지와 어떻게 방어할 수 있는지를 함께 정리하는 것이 중요하다.

이전 글에서는 웹 보안에서 자주 등장하는 기본적인 취약점들을 정리했다.  

이번 글에서는 기본적인 웹 취약점에서 조금 더 나아가, 서버가 요청을 처리하는 방식, API가 데이터를 반영하는 방식, 서비스의 동작 흐름, 캐시와 프록시 같은 웹 구조와 관련된 취약점들을 정리해보려고 한다.

웹 취약점은 단순히 특정 입력값을 넣었을 때 발생하는 문제만을 의미하지 않는다.  
서버가 외부 요청을 보내는 방식, 사용자 입력값을 객체에 반영하는 방식, 서비스가 정해진 순서대로 동작한다고 가정하는 방식, 여러 서버가 HTTP 요청을 해석하는 방식 차이에서도 취약점은 발생할 수 있다.

이번 글에서 정리할 취약점은 다음과 같다.

- SSRF
- SSTI
- Mass Assignment
- Business Logic Vulnerability
- Web Cache Poisoning
- HTTP Request Smuggling

# 웹 취약점을 더 깊게 볼 때 중요한 관점

기본적인 웹 취약점을 공부할 때는 다음과 같은 질문이 중요했다.

> 사용자의 입력값을 서버가 어떻게 처리하는가?  
> 사용자가 해당 기능이나 데이터에 접근할 권한이 있는가?  
> 서버가 클라이언트에서 전달된 값을 그대로 신뢰하고 있지는 않은가?

조금 더 깊게 들어가면 다음과 같은 질문도 함께 생각해볼 수 있다.

> 사용자가 전달한 URL을 서버가 대신 요청하고 있지는 않은가?  
> 입력값이 단순한 데이터가 아니라 서버 내부 로직에서 다시 해석되고 있지는 않은가?  
> 사용자가 보내지 않아야 할 필드까지 서버가 그대로 반영하고 있지는 않은가?  
> 서비스가 정해진 순서대로만 동작할 것이라고 가정하고 있지는 않은가?  
> 캐시나 프록시 서버가 요청과 응답을 예상과 다르게 처리할 가능성은 없는가?

웹 서비스는 단순히 브라우저와 서버 하나만으로 동작하지 않는다.  
실제 서비스에서는 API, 템플릿 엔진, 캐시 서버, 프록시 서버, 백엔드 서버 등 여러 구성 요소가 함께 동작한다.  
따라서 웹 취약점을 이해할 때는 사용자의 입력값뿐 아니라, 그 입력값이 서비스 내부에서 어디까지 전달되고 어떻게 처리되는지도 함께 봐야 한다.

## 1. SSRF

### SSRF란?

SSRF는 Server-Side Request Forgery의 약자이다.  
사용자가 전달한 URL을 서버가 대신 요청하는 기능에서, 공격자가 의도한 주소로 서버가 요청을 보내게 만드는 취약점이다.

웹 서비스에서는 이미지 URL을 받아 서버가 대신 다운로드하거나, 외부 API를 호출하거나, 웹훅을 전송하거나, 특정 URL의 미리보기를 생성하는 기능이 사용될 수 있다.  
이때 사용자가 입력한 URL을 충분히 검증하지 않으면, 공격자는 서버가 원래 접근하면 안 되는 내부 주소나 제한된 자원으로 요청을 보내도록 만들 수 있다.

핵심은 다음과 같다.

> 사용자가 전달한 URL을 서버가 신뢰하고 대신 요청할 때 SSRF가 발생할 수 있다.

### 발생 가능한 기능

SSRF는 주로 서버가 외부 자원에 직접 요청을 보내는 기능에서 발생한다.

예를 들면 다음과 같은 기능이 있다.

- 이미지 URL 업로드
- 프로필 사진 URL 등록
- 웹훅 전송
- 외부 API 연동
- URL 미리보기 생성
- 파일 다운로드 기능
- PDF 생성 기능
- RSS 피드 가져오기

단순히 사용자가 URL을 입력하는 것만으로 문제가 되는 것은 아니다.  
그 URL을 서버가 직접 요청하고, 요청 가능한 대상을 충분히 제한하지 않을 때 문제가 된다.

### 공격으로 이어지는 흐름

SSRF가 발생하면 공격자는 서버의 네트워크 위치를 악용할 수 있다.  
외부 사용자는 직접 접근할 수 없는 내부 자원이라도, 서버는 접근 가능한 경우가 있기 때문이다.

SSRF는 다음과 같은 공격으로 이어질 수 있다.

- 내부망 서비스 접근
- 로컬호스트 서비스 접근
- 관리자 페이지 접근
- 내부 API 호출
- 클라우드 메타데이터 조회
- 내부 포트 스캔
- 민감한 정보 노출
- 다른 취약점과 결합한 추가 공격

예를 들어 외부에서는 접근할 수 없는 내부 관리자 페이지가 있다고 하더라도, 애플리케이션 서버가 해당 주소에 접근할 수 있다면 SSRF를 통해 요청이 전달될 수 있다.

### 다른 취약점과의 연결

SSRF는 단독으로도 위험하지만, 다른 취약점과 연결되면 더 큰 피해로 이어질 수 있다.

예를 들어 내부 관리자 기능에 접근 통제 문제가 있다면, SSRF를 통해 내부 관리자 페이지를 호출한 뒤 추가적인 권한 우회로 이어질 수 있다.

또한 클라우드 환경에서 메타데이터 서비스에 접근할 수 있다면 인증 정보나 토큰이 노출될 수 있고, 이후 다른 서비스 접근으로 이어질 수 있다.

즉, SSRF는 단순한 외부 요청 문제가 아니라, 서버가 가진 네트워크 권한을 공격자가 대신 사용하는 문제라고 볼 수 있다.

### 방어 방법

SSRF를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 허용된 도메인만 요청할 수 있도록 Allowlist 적용
- 사용자가 입력한 URL 검증
- 내부 IP 대역과 로컬호스트 접근 차단
- 리다이렉트 처리 시 최종 목적지까지 검증
- DNS Rebinding에 대한 고려
- 불필요한 외부 요청 기능 최소화
- 서버가 접근할 수 있는 네트워크 범위 최소화
- 민감한 내부 서비스 분리
- 응답 내용을 그대로 사용자에게 반환하지 않기

가장 중요한 것은 사용자가 입력한 URL을 그대로 신뢰하지 않는 것이다.  
서버가 외부 요청을 보내야 하는 기능이라면, 어떤 대상에 요청할 수 있는지 명확하게 제한해야 한다.

## 2. SSTI

### SSTI란?

SSTI는 Server-Side Template Injection의 약자이다.  
사용자 입력값이 서버 템플릿 안에 안전하지 않게 삽입되어, 단순한 데이터가 아니라 템플릿 문법으로 해석되는 취약점이다.

웹 서비스는 서버에서 HTML을 동적으로 만들기 위해 템플릿 엔진을 사용할 수 있다.  
예를 들어 사용자 이름, 게시글 제목, 상품 정보 등을 템플릿에 넣어 최종 HTML 페이지를 만든다.

이때 사용자 입력값을 템플릿에 안전하게 전달하지 않고 템플릿 코드 자체처럼 처리하면, 공격자가 템플릿 표현식을 삽입해 서버 내부에서 실행되도록 만들 수 있다.

핵심은 다음과 같다.

> 원래는 데이터로 처리되어야 할 사용자 입력값이 서버 템플릿 문법으로 해석될 때 SSTI가 발생한다.

### 발생 가능한 기능

SSTI는 서버 측 템플릿 엔진을 사용하는 기능에서 발생할 수 있다.

예를 들면 다음과 같은 기능이 있다.

- 이메일 템플릿
- 알림 메시지 생성
- 프로필 소개 페이지
- 게시글 미리보기
- 마케팅 페이지 생성
- CMS 기능
- 사용자 정의 문구가 포함되는 페이지
- 동적 HTML 생성 기능

특히 사용자가 일부 문구나 레이아웃을 직접 작성할 수 있는 기능이 있다면, 입력값이 템플릿으로 처리되는지 주의해서 봐야 한다.

### 공격으로 이어지는 흐름

SSTI가 발생하면 공격자는 템플릿 엔진이 제공하는 기능을 악용할 수 있다.  
템플릿 엔진의 종류와 설정에 따라 단순한 값 노출부터 서버 내부 객체 접근, 심한 경우 원격 코드 실행으로 이어질 수 있다.

SSTI는 다음과 같은 공격으로 이어질 수 있다.

- 서버 내부 변수 노출
- 환경 정보 노출
- 템플릿 객체 접근
- 민감한 설정값 노출
- 서버 파일 접근
- 서버 측 코드 실행
- 원격 코드 실행

단순히 화면에 값이 출력되는 문제처럼 보일 수 있지만, 브라우저가 아니라 서버 내부에서 해석된다는 점에서 위험도가 커질 수 있다.

### XSS와의 차이

SSTI와 XSS는 모두 사용자 입력값이 의도하지 않은 방식으로 해석된다는 공통점이 있다.  
하지만 해석되는 위치가 다르다.

- XSS는 사용자 입력값이 브라우저에서 HTML 또는 JavaScript로 해석되는 문제이다.
- SSTI는 사용자 입력값이 서버의 템플릿 엔진에서 템플릿 문법으로 해석되는 문제이다.

즉, XSS는 클라이언트 측 코드 실행 문제이고, SSTI는 서버 측 처리 문제라고 볼 수 있다.

### 다른 취약점과의 연결

SSTI는 서버 내부 정보 노출이나 원격 코드 실행으로 이어질 수 있기 때문에 다른 취약점의 발판이 될 수 있다.

예를 들어 서버의 설정 정보나 비밀 키가 노출되면 세션 위조나 추가적인 인증 공격으로 이어질 수 있다.

또한 템플릿을 통해 서버 파일에 접근할 수 있다면, 설정 파일이나 소스 코드가 노출되어 이후 다른 취약점 탐색이 쉬워질 수 있다.

### 방어 방법

SSTI를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 사용자 입력값을 템플릿 코드로 직접 렌더링하지 않기
- 템플릿과 데이터를 분리해서 처리
- 안전한 템플릿 렌더링 방식 사용
- 사용자에게 템플릿 문법 작성 기능을 제공하지 않기
- 필요하다면 샌드박스 기능 적용
- 템플릿 엔진의 위험한 기능 비활성화
- 서버 측 코드 실행으로 이어질 수 있는 객체 접근 제한
- 입력값 검증과 출력 처리 병행

가장 중요한 것은 사용자 입력값을 템플릿 자체로 해석하지 않도록 하는 것이다.  
사용자 입력값은 템플릿에 들어가는 데이터로만 처리되어야 한다.

## 3. Mass Assignment

### Mass Assignment란?

Mass Assignment는 사용자가 보낸 요청 데이터가 서버의 객체 속성에 자동으로 연결되는 과정에서, 원래 수정되면 안 되는 필드까지 함께 반영되는 취약점이다.

개발 편의를 위해 일부 프레임워크는 HTTP 요청의 값을 객체 속성에 자동으로 매핑하는 기능을 제공한다.  
예를 들어 사용자가 회원가입 시 `username`, `email`, `password` 값을 보내면, 서버가 이를 사용자 객체에 자동으로 넣어주는 방식이다.

하지만 서버가 허용해야 할 필드를 명확하게 제한하지 않으면, 공격자는 원래 화면에는 없던 `role`, `is_admin`, `balance` 같은 필드를 추가로 보내 서버 객체에 반영되도록 시도할 수 있다.

핵심은 다음과 같다.

> 사용자가 보낸 값 중 서버가 받아야 할 필드를 제한하지 않으면, 의도하지 않은 속성까지 수정될 수 있다.

### 발생 가능한 기능

Mass Assignment는 주로 사용자의 입력값이 객체에 한 번에 반영되는 기능에서 발생한다.

예를 들면 다음과 같은 기능이 있다.

- 회원가입
- 프로필 수정
- 주소 수정
- 상품 등록
- 주문 정보 수정
- 관리자 기능 일부
- REST API의 생성 및 수정 요청

특히 JSON 기반 API에서는 클라이언트가 어떤 필드를 보내는지 직접 조작하기 쉬우므로 주의가 필요하다.

### 공격으로 이어지는 흐름

Mass Assignment가 발생하면 공격자는 서버가 원래 수정하게 해서는 안 되는 값을 변경하려고 시도할 수 있다.

다음과 같은 문제가 발생할 수 있다.

- 일반 사용자의 관리자 권한 획득
- 계정 상태 변경
- 가격이나 할인율 조작
- 잔액 변경
- 승인 상태 우회
- 비공개 필드 수정
- 다른 객체 속성 조작

예를 들어 프로필 수정 API가 사용자의 이름과 이메일만 바꾸도록 의도되었는데, 서버가 요청 본문의 모든 필드를 그대로 사용자 객체에 반영한다면 공격자가 `is_admin=true` 같은 값을 추가로 보내 권한 상승을 시도할 수 있다.

### Broken Access Control과의 차이

Mass Assignment와 Broken Access Control은 둘 다 권한 문제와 연결될 수 있지만, 발생 지점이 다르다.

- Broken Access Control은 사용자가 접근하면 안 되는 데이터나 기능에 접근하는 문제이다.
- Mass Assignment는 사용자가 보낸 데이터 중 수정하면 안 되는 필드까지 서버가 반영하는 문제이다.

즉, Broken Access Control은 “접근할 수 있느냐”의 문제이고, Mass Assignment는 “어떤 값을 수정할 수 있느냐”의 문제라고 볼 수 있다.

### 다른 취약점과의 연결

Mass Assignment는 접근 통제 취약점과 연결되면 피해가 더 커질 수 있다.

예를 들어 어떤 사용자가 자신의 프로필만 수정할 수 있어야 하는데 IDOR까지 존재한다면, 공격자는 다른 사용자의 객체를 선택한 뒤 원래 수정 불가능한 필드까지 조작하려고 시도할 수 있다.

또한 비즈니스 로직 취약점과 연결되어 주문 상태, 할인 여부, 결제 완료 여부 같은 값을 직접 조작하는 방식으로 악용될 수 있다.

### 방어 방법

Mass Assignment를 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 서버에서 허용할 필드만 명시적으로 지정
- Allowlist 기반 바인딩 사용
- 사용자가 수정할 수 없는 필드는 요청 본문에서 무시
- DTO, ViewModel 등을 사용해 입력 객체 분리
- 관리자 전용 필드와 일반 사용자 입력 필드 분리
- 민감한 필드에 대한 서버 측 검증
- API 명세에 없는 필드가 들어왔을 때 처리 방식 점검

가장 중요한 것은 사용자가 보낼 수 있는 값과 실제로 서버가 반영해야 하는 값을 구분하는 것이다.  
클라이언트 화면에 입력칸이 없다고 해서 공격자가 해당 필드를 보낼 수 없는 것은 아니다.

## 4. Business Logic Vulnerability

### Business Logic Vulnerability란?

Business Logic Vulnerability는 서비스가 의도한 업무 흐름이나 규칙을 공격자가 예상과 다르게 이용해, 보안상 문제가 발생하는 취약점이다.

많은 취약점은 입력값 검증 부족, 인증 실패, 권한 확인 누락처럼 기술적인 보안 통제가 잘못되어 발생한다.  
반면 Business Logic Vulnerability는 기능 자체는 정상적으로 동작하지만, 사용자가 그 기능을 예상하지 못한 방식으로 사용했을 때 문제가 발생한다.

핵심은 다음과 같다.

> 기능이 정상적으로 동작하더라도, 서비스가 의도한 규칙과 흐름을 우회할 수 있다면 비즈니스 로직 취약점이 될 수 있다.

### 발생 가능한 기능

Business Logic Vulnerability는 서비스마다 다르게 나타날 수 있다.

예를 들면 다음과 같은 기능에서 생각해볼 수 있다.

- 쿠폰 사용
- 포인트 적립
- 결제
- 환불
- 회원 등급
- 재고 차감
- 추천인 보상
- 이메일 인증
- 비밀번호 재설정
- 주문 단계 진행

특정 페이로드 하나로 공통적으로 찾는 취약점이 아니라, 서비스의 목적과 흐름을 이해해야 발견할 수 있다.

### 대표적인 예시

Business Logic Vulnerability는 다음과 같은 방식으로 나타날 수 있다.

- 한 번만 사용할 수 있는 쿠폰을 여러 번 사용하는 경우
- 결제 전에 주문 완료 상태로 넘어가는 경우
- 이메일 인증 단계를 건너뛰고 계정을 활성화하는 경우
- 정해진 순서를 건너뛰고 마지막 단계만 직접 요청하는 경우
- 할인 금액이 상품 가격보다 커져 음수 결제가 발생하는 경우
- 포인트 적립과 환불 흐름을 반복해 이득을 얻는 경우
- 재고가 없는 상품을 구매할 수 있는 경우

이처럼 입력값 자체가 이상하지 않아 보여도, 서비스의 규칙이 무너진다면 보안 문제가 될 수 있다.

### 공격으로 이어지는 흐름

Business Logic Vulnerability가 발생하면 공격자는 서비스의 정상 기능을 악용해 이득을 얻을 수 있다.

다음과 같은 문제가 발생할 수 있다.

- 금전적 손실
- 할인이나 보상 중복 사용
- 유료 기능 무단 이용
- 인증 절차 우회
- 결제 흐름 우회
- 재고 조작
- 비정상적인 계정 상태 획득
- 서비스 정책 무력화

다른 취약점처럼 눈에 띄는 에러 메시지나 공격 구문이 없을 수 있기 때문에, 자동화 도구만으로는 발견하기 어려운 편이다.

### Race Condition과의 연결

Business Logic Vulnerability는 Race Condition과 연결될 수 있다.

예를 들어 한 번만 사용 가능한 쿠폰이 있다고 가정한다.  
서버가 쿠폰 사용 가능 여부를 확인한 뒤 사용 처리까지 하는 사이에 여러 요청이 동시에 들어오면, 쿠폰이 여러 번 사용될 수 있다.

이 경우 문제의 핵심은 단순히 입력값이 아니라, 서비스가 상태 변화를 처리하는 타이밍과 흐름에 있다.

### 다른 취약점과의 연결

Business Logic Vulnerability는 Mass Assignment나 Broken Access Control과 함께 나타날 수 있다.

예를 들어 주문 상태를 사용자가 직접 수정할 수 있는 Mass Assignment가 존재한다면, 결제 전 상태에서 주문 완료 상태로 바꾸는 식의 비즈니스 로직 우회가 가능해질 수 있다.

또한 특정 단계의 API에 대한 접근 통제가 부족하다면, 정해진 절차를 건너뛰고 중요한 기능을 직접 호출할 수 있다.

### 방어 방법

Business Logic Vulnerability를 줄이기 위해서는 다음과 같은 방법이 필요하다.

- 서비스 흐름에 대한 서버 측 검증
- 각 단계가 올바른 순서로 수행되었는지 확인
- 한 번만 사용할 수 있는 기능은 서버에서 횟수 제한
- 가격, 할인, 포인트 계산을 서버에서 재검증
- 중요 상태 변경 시 현재 상태와 이전 상태를 함께 확인
- 동시 요청에 대한 처리 방식 고려
- 비정상적인 사용 흐름에 대한 테스트
- 예상 가능한 오용 사례를 설계 단계에서 검토

Business Logic Vulnerability는 단순한 필터링만으로 막기 어렵다.  
서비스가 어떤 순서로 동작해야 하는지, 사용자가 어떤 방식으로 오용할 수 있는지를 함께 생각해야 한다.

## 5. Web Cache Poisoning

### Web Cache Poisoning이란?

Web Cache Poisoning은 캐시 서버가 저장한 응답을 다른 사용자에게 재사용하는 특성을 악용해, 공격자가 만든 악성 응답이 캐시에 저장되고 이후 다른 사용자에게 전달되도록 만드는 공격이다.

웹 서비스는 성능을 높이기 위해 자주 요청되는 응답을 캐시에 저장할 수 있다.  
이때 캐시는 요청의 일부 값들을 기준으로 같은 응답을 재사용하는데, 이를 캐시 키라고 한다.

문제는 백엔드 서버가 응답을 만들 때 사용하는 입력값 중 일부가 캐시 키에는 포함되지 않을 수 있다는 점이다.  
공격자가 캐시 키에 포함되지 않는 값을 조작해 악성 응답을 만들고, 그 응답이 캐시에 저장되면 이후 다른 사용자도 같은 악성 응답을 받을 수 있다.

핵심은 다음과 같다.

> 서버는 응답 생성에 사용하지만 캐시는 구분하지 않는 입력값이 있을 때, 악성 응답이 다른 사용자에게 재사용될 수 있다.

### 발생 원인

Web Cache Poisoning은 주로 다음과 같은 상황에서 발생한다.

- 응답 생성에 사용되는 입력값이 캐시 키에 포함되지 않는 경우
- 특정 헤더 값을 서버가 신뢰하는 경우
- 캐시와 백엔드 서버가 요청을 다르게 해석하는 경우
- 캐시 가능한 응답에 사용자 제어 값이 반영되는 경우
- 캐시 정책이 잘못 설정된 경우

예를 들어 백엔드 서버가 특정 헤더 값을 사용해 페이지 안의 스크립트 주소를 만들지만, 캐시는 그 헤더를 구분하지 않는다면 공격자는 악성 주소가 포함된 응답을 캐시에 저장하려고 시도할 수 있다.

### 공격으로 이어지는 흐름

Web Cache Poisoning이 발생하면 공격자는 한 번의 요청으로 여러 사용자에게 영향을 줄 수 있다.

다음과 같은 공격으로 이어질 수 있다.

- 악성 스크립트 배포
- 대규모 XSS
- 악성 리다이렉트
- 로그인 페이지 변조
- 피싱 페이지 삽입
- 서비스 장애 유발
- 특정 기능의 지속적인 오작동

일반적인 XSS는 특정 사용자 한 명이 조작된 응답을 받는 구조일 수 있지만, Web Cache Poisoning과 결합되면 캐시를 통해 여러 사용자에게 같은 악성 응답이 반복적으로 전달될 수 있다.

### XSS와의 연결

Web Cache Poisoning은 XSS와 연결될 수 있다.

예를 들어 공격자가 응답 안에 악성 스크립트가 포함되도록 만들고, 그 응답이 캐시에 저장된다면 이후 해당 페이지를 방문하는 여러 사용자에게 스크립트가 실행될 수 있다.

즉, XSS가 브라우저에서의 코드 실행 문제라면, Web Cache Poisoning은 그 악성 응답을 여러 사용자에게 퍼뜨리는 통로가 될 수 있다.

### HTTP Request Smuggling과의 연결

Web Cache Poisoning은 HTTP Request Smuggling과도 연결될 수 있다.

프론트엔드와 백엔드 서버가 요청을 다르게 해석해 응답이 꼬이게 되면, 공격자가 의도한 응답이 다른 요청에 매칭되어 캐시에 저장될 수 있다.

이 경우 하나의 취약점이 다른 취약점을 더 쉽게 악용할 수 있는 기반이 된다.

### 방어 방법

Web Cache Poisoning을 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 응답 생성에 영향을 주는 모든 입력값을 파악
- 캐시 키에 포함되지 않는 사용자 제어 값 최소화
- 불필요한 헤더를 응답 생성에 사용하지 않기
- 사용자별 응답은 캐시하지 않기
- 캐시 정책을 명확하게 설정
- 민감한 페이지에 대한 캐싱 제한
- 프록시와 백엔드의 요청 해석 차이 점검
- 캐시 동작을 고려한 보안 테스트 수행

가장 중요한 것은 어떤 값이 응답을 바꾸고, 어떤 값이 캐시에서 같은 요청으로 취급되는지를 함께 보는 것이다.

## 6. HTTP Request Smuggling

### HTTP Request Smuggling이란?

HTTP Request Smuggling은 프론트엔드 서버와 백엔드 서버가 하나의 HTTP 요청이 어디서 끝나는지를 서로 다르게 해석할 때 발생하는 취약점이다.

실제 웹 서비스에서는 사용자의 요청이 바로 애플리케이션 서버로 가지 않고, 로드 밸런서나 리버스 프록시 같은 프론트엔드 서버를 거친 뒤 백엔드 서버로 전달되는 경우가 많다.

이때 두 서버가 `Content-Length`와 `Transfer-Encoding` 같은 헤더를 서로 다르게 처리하면, 공격자가 애매하게 구성한 요청을 이용해 두 서버의 요청 경계를 어긋나게 만들 수 있다.

핵심은 다음과 같다.

> 같은 HTTP 요청을 여러 서버가 서로 다르게 해석할 때 HTTP Request Smuggling이 발생할 수 있다.

### 발생 원인

HTTP Request Smuggling은 주로 다음과 같은 상황에서 발생한다.

- 프론트엔드와 백엔드 서버가 요청 길이를 다르게 해석하는 경우
- `Content-Length`와 `Transfer-Encoding` 헤더를 다르게 처리하는 경우
- 여러 서버가 서로 다른 HTTP 구현을 사용하는 경우
- HTTP/1.1 요청 처리 방식이 일관되지 않은 경우
- 프록시와 백엔드 사이의 요청 정규화가 부족한 경우

하나의 서버만 보면 정상처럼 보여도, 여러 서버가 함께 동작할 때 해석 차이가 생기면 문제가 될 수 있다.

### 공격으로 이어지는 흐름

HTTP Request Smuggling이 발생하면 공격자는 자신의 요청 일부를 다음 사용자의 요청 앞에 끼워 넣거나, 서버의 요청 처리 순서를 어긋나게 만들 수 있다.

다음과 같은 공격으로 이어질 수 있다.

- 다른 사용자의 요청에 영향
- 요청 우회
- 접근 통제 우회
- 캐시 중독
- 악성 응답 전달
- 세션 관련 공격
- 내부 요청 조작
- 프론트엔드 보안 통제 우회

예를 들어 프론트엔드 서버는 하나의 요청이 끝났다고 판단했지만, 백엔드 서버는 일부 데이터를 다음 요청의 시작으로 해석한다면, 이후 들어오는 정상 사용자의 요청이 공격자의 의도와 섞여 처리될 수 있다.

### 주요 유형

HTTP Request Smuggling은 요청 길이 해석 방식에 따라 대표적으로 다음과 같은 유형으로 설명할 수 있다.

- CL.TE
- TE.CL
- TE.TE

여기서 `CL`은 `Content-Length`, `TE`는 `Transfer-Encoding`을 의미한다.

- CL.TE는 프론트엔드가 `Content-Length`를 기준으로 처리하고, 백엔드가 `Transfer-Encoding`을 기준으로 처리하는 경우이다.
- TE.CL은 프론트엔드가 `Transfer-Encoding`을 기준으로 처리하고, 백엔드가 `Content-Length`를 기준으로 처리하는 경우이다.
- TE.TE는 양쪽 모두 `Transfer-Encoding`을 지원하지만, 헤더를 다르게 해석하는 경우이다.

핵심은 어떤 조합이든 여러 서버가 요청의 끝을 다르게 본다는 점이다.

### Web Cache Poisoning과의 연결

HTTP Request Smuggling은 Web Cache Poisoning으로 이어질 수 있다.

공격자가 백엔드 서버에 전달되는 요청 흐름을 꼬이게 만들면, 원래 다른 응답이어야 할 내용이 특정 캐시 키에 저장되도록 유도할 수 있다.

이렇게 되면 이후 다른 사용자가 같은 자원에 접근할 때 악성 응답을 받게 될 수 있다.

### 다른 취약점과의 연결

HTTP Request Smuggling은 단독으로도 위험하지만, 프록시나 백엔드의 보안 통제를 우회하는 데 사용될 수 있다.

예를 들어 프론트엔드에서는 차단되는 요청이 백엔드에는 다르게 전달되거나, 특정 요청이 다른 사용자 요청과 섞이면서 접근 통제나 인증 처리에 영향을 줄 수 있다.

즉, HTTP Request Smuggling은 단순히 요청 하나를 조작하는 문제가 아니라, 여러 서버 사이의 신뢰 관계와 요청 흐름을 무너뜨리는 문제라고 볼 수 있다.

### 방어 방법

HTTP Request Smuggling을 방어하기 위해서는 다음과 같은 방법이 필요하다.

- 프론트엔드와 백엔드의 HTTP 요청 해석 방식 일치
- 모호한 요청 차단
- `Content-Length`와 `Transfer-Encoding`이 함께 존재하는 비정상 요청 거부
- 요청 정규화 적용
- 프록시와 백엔드 서버 최신 버전 유지
- 서버 간 연결 재사용 방식 점검
- HTTP/2에서 HTTP/1.1로 변환되는 구간 점검
- 보안 장비와 애플리케이션 서버의 요청 처리 차이 테스트

가장 중요한 것은 한 서버에서만 요청을 정상으로 보는 것이 아니라, 전체 요청 경로에 있는 모든 서버가 같은 방식으로 요청을 해석하도록 만드는 것이다.

# 취약점 간 연결 흐름

웹 취약점은 하나만 단독으로 발생하기도 하지만, 여러 취약점이 연결되면서 더 큰 피해로 이어질 수 있다.

### SSRF → 내부 서비스 접근 → 추가 공격

SSRF가 발생하면 외부에서 직접 접근할 수 없는 내부 서비스로 요청을 보낼 수 있다.  
내부 관리자 페이지나 메타데이터 서비스에 접근할 수 있다면, 이후 정보 노출이나 추가적인 권한 악용으로 이어질 수 있다.

### SSTI → 서버 내부 정보 노출 → 원격 코드 실행

SSTI는 단순한 템플릿 표현식 실행에서 시작할 수 있지만, 서버 내부 객체나 설정값에 접근할 수 있다면 민감한 정보 노출이나 원격 코드 실행으로 이어질 수 있다.

### Mass Assignment → 권한 필드 조작 → 관리자 권한 획득

Mass Assignment가 존재하면 사용자가 원래 수정할 수 없어야 하는 필드를 조작하려고 시도할 수 있다.  
예를 들어 `role`, `is_admin` 같은 값이 그대로 반영된다면 권한 상승으로 이어질 수 있다.

### Business Logic Vulnerability → 서비스 흐름 우회 → 금전적 피해

비즈니스 로직 취약점이 존재하면 결제, 환불, 쿠폰, 포인트 같은 기능을 정상 흐름과 다르게 이용할 수 있다.  
기술적인 에러가 없어 보여도 실제 서비스에는 직접적인 손해가 발생할 수 있다.

### Web Cache Poisoning → 악성 응답 저장 → 여러 사용자에게 영향

Web Cache Poisoning이 발생하면 한 번 만들어진 악성 응답이 캐시에 저장되어 여러 사용자에게 반복적으로 전달될 수 있다.  
XSS와 결합되면 피해 범위가 크게 넓어질 수 있다.

### HTTP Request Smuggling → 요청 흐름 교란 → 캐시 중독 또는 보안 통제 우회

HTTP Request Smuggling은 프론트엔드와 백엔드의 요청 해석 차이를 이용한다.  
이로 인해 요청 흐름이 어긋나면 캐시 중독, 접근 통제 우회, 다른 사용자의 요청 영향 등으로 이어질 수 있다.

## 정리

이번 글에서 정리한 취약점들은 기본적인 웹 취약점보다 조금 더 서비스 내부 구조와 동작 흐름을 함께 봐야 이해할 수 있는 주제들이다.

- SSRF는 사용자가 전달한 URL을 서버가 대신 요청할 때 발생할 수 있다.
- SSTI는 사용자 입력값이 서버 템플릿 문법으로 해석될 때 발생한다.
- Mass Assignment는 사용자가 보낸 값 중 수정되면 안 되는 필드까지 객체에 반영될 때 발생한다.
- Business Logic Vulnerability는 서비스가 의도한 흐름이나 규칙을 우회할 수 있을 때 발생한다.
- Web Cache Poisoning은 악성 응답이 캐시에 저장되어 다른 사용자에게 재사용될 때 발생한다.
- HTTP Request Smuggling은 여러 서버가 같은 요청의 경계를 다르게 해석할 때 발생한다.

이 취약점들은 각각 다른 방식으로 발생하지만, 공통적으로 다음과 같은 질문과 연결된다.

> 서버가 사용자의 입력값을 어디까지 신뢰하고 있는가?  
> 서비스는 사용자가 항상 정상적인 순서로만 기능을 사용할 것이라고 가정하고 있지는 않은가?  
> 여러 구성 요소가 같은 요청을 같은 방식으로 해석하고 있는가?  
> 보이지 않는 내부 처리 과정에서 사용자가 제어할 수 있는 값이 예상보다 더 큰 영향을 주고 있지는 않은가?

웹 취약점을 공부할 때는 공격 기법의 이름을 많이 아는 것보다,  
각 취약점이 어떤 구조에서 발생하고 왜 위험한지를 이해하는 것이 더 중요하다.
